# Deployment Readiness Audit

Date: 2026-07-21
Repository: Communication-Agent-AI
Scope: Production deployment readiness for a public portfolio demo
Change policy: Audit only. No runtime code, dependency, infra, or deployment file modifications were made.

## Executive Summary
The project has a workable deployment foundation (FastAPI app, Dockerfile, Nginx template, Vultr script, JWT auth, CI checks), but it is not safely deployable as-is for a public demo without targeted deployment fixes.

Key blockers are:
- deployment script/API base mismatch that can leave frontend pointed at the wrong API,
- insecure default production posture (development env default, root-run service, no TLS by default),
- persistence strategy not explicitly handled for containerized deployment,
- Linux packaging risk for MediaPipe/OpenCV in the current slim image.

Current readiness verdict: READY AFTER FIXES

## Current Architecture
Implemented architecture today:
- Frontend: static HTML/CSS/JS in frontend/
- Backend: FastAPI app in backend/main.py
- App entrypoint: uvicorn serving backend.main:app
- Authentication: JWT Bearer tokens via backend/auth/auth_handler.py
- App config: environment variables loaded in backend/core/settings.py
- Data layer: SQLite database file communication_bridge.db via backend/database/db.py
- AI integration: Google Gemini client with fallback behavior in backend/services/llm_client.py
- Vision pipeline: OpenCV + MediaPipe in backend/services/vision_service.py
- Reverse proxy option: nginx.conf (frontend static + API proxy)
- Vultr option: deploy_vultr.sh installs system packages, runs backend with systemd, serves frontend via Nginx

### Effective request path in VPS model
- Browser requests static frontend from Nginx location /
- Frontend calls API_BASE + route
- Nginx /api/ rewrites and proxies to localhost:8000
- FastAPI handles route and uses SQLite + agents + LLM as needed

## Production Startup Command
Exact implemented startup commands:
- Docker: CMD in Dockerfile
  - python -m uvicorn backend.main:app --host 0.0.0.0 --port 8000
- Systemd in deploy_vultr.sh
  - ExecStart=/usr/bin/python3 main.py
  - WorkingDirectory=$PROJECT_DIR/backend
  - main.py then runs uvicorn.run(app, host=settings.host, port=settings.port)

Recommended production command form:
- python -m uvicorn backend.main:app --host 0.0.0.0 --port 8000

## Dockerfile Production Readiness
File audited: Dockerfile

Strengths:
- Uses Python 3.11-slim (aligned with CI Python 3.11)
- Defines explicit app command via uvicorn
- Uses pinned dependency file

Gaps and risks:
- No OS-level runtime packages for OpenCV/MediaPipe Linux compatibility
- No non-root user
- No healthcheck instruction
- No explicit APP_ENV=production default
- No volume declaration or persistence guidance for SQLite file
- Includes frontend files but backend does not serve them directly

Assessment: Functional for API-only smoke runs, not production-ready for reliable vision + secure posture without hardening.

## deploy_vultr.sh Safety and Functionality
File audited: deploy_vultr.sh

What works:
- Automates host setup, package install, Nginx, systemd service, firewall
- Proxies /api/ to backend and serves frontend files from disk

Critical/High issues:
- API base rewrite likely fails against current frontend code:
  - Script searches for const API_BASE = 'http://localhost:8000';
  - Current frontend files use a different default value;
  - Result: frontend may still point to old/external API URL after deploy.
- Service runs as root user.
- No TLS provisioning in-script (HTTP deployment by default).
- Uses global pip install rather than isolated venv for runtime app.
- Gemini key prompt is plain input (not hidden).
- Server name is raw IP; domain and cert path not automated.

Assessment: Not safe enough as-is for public deployment without fixes.

## nginx.conf Correctness for Current FastAPI App
File audited: nginx.conf

What is correct:
- /api/ rewrite and proxy pattern can route to FastAPI endpoints correctly
- /docs and /openapi.json are proxied
- Static frontend serving and cache headers present
- Basic security headers included

Caveats:
- Hardcoded root path assumes /root/communication-bridge-ai/frontend
- HTTP-only default unless TLS block is manually enabled
- Health check location /health proxies to / (no dedicated backend /health endpoint)
- Config shape differs slightly from inline config generated by deploy_vultr.sh (operational drift risk)

Assessment: Close, but requires environment-specific alignment and TLS enablement.

## SQLite Suitability for First Public Deployment
Current state:
- SQLite file communication_bridge.db is created in process working directory.

Suitability:
- Suitable for low-traffic portfolio demo with single instance.
- Not suitable for scaled or multi-instance deployment.

Operational requirements:
- Ensure persistent disk/volume backup strategy.
- Avoid multi-writer/multi-replica topology.
- Define retention/backup plan for demo data.

## MediaPipe and OpenCV Compatibility in Docker/Linux
Dependencies:
- mediapipe==0.10.8
- opencv-python==4.8.1.78

Observed risk indicators:
- Local pip-audit dependency resolution failed for mediapipe==0.10.8 on Python 3.14.
- Docker image uses python:3.11-slim, but lacks explicit Linux runtime libs often needed by OpenCV stacks.

Assessment:
- More reliable on Python 3.11 host/container than newer interpreters.
- Current Docker image may fail at runtime for vision features without additional OS packages.
- Vision should be considered at-risk until containerized runtime verification is completed.

## Frontend Deployment Model
Current implementation:
- Backend does not mount static frontend routes.
- Frontend is standalone static files that call API endpoints via API_BASE.

Implication:
- Frontend requires separate static hosting layer (Nginx or equivalent) or explicit backend static serving (not currently implemented).
- Dockerfile copying frontend alone is insufficient unless another process serves those files.

## CORS Production Configuration
Current defaults in .env.example are localhost origins.

Production requirement:
- Set CORS_ORIGINS to actual public frontend origin(s).
- Keep CORS_ALLOW_CREDENTIALS aligned with auth strategy.
- Do not use wildcard origins for authenticated endpoints.

## Browser Permissions and Real-Time Features
Deployment-relevant constraints:
- Webcam and microphone access are browser features and require user permission.
- Browser speech and media APIs generally require secure context (HTTPS) on public domains.
- Server-side does not access client webcam directly; client sends frame payloads to backend.

Impact:
- Public demo should run over HTTPS to reduce permission friction and avoid browser restrictions.

## Persistent Storage Requirements
Required for correct app behavior:
- SQLite database persistence (users, sessions, logs, messages, gesture history)
- If deployed in container platform with ephemeral FS, a persistent volume is required.

Without persistence:
- User accounts and history are lost on restart/redeploy.

## Security Issues Before Public Deployment
Must-fix before public launch:
- Enforce production environment settings and strong JWT secret.
- Enable HTTPS termination (TLS cert, redirect HTTP to HTTPS).
- Do not run backend service as root.
- Fix frontend API base deployment wiring to avoid stale external endpoint target.

High-priority hardening:
- Restrict CORS to exact frontend origin(s).
- Add request size/rate protections at proxy and app edge.
- Review token storage model (localStorage/sessionStorage has XSS exposure risk).
- Add monitoring and alerting.

## Deployment Blockers
Primary blockers for a reliable public demo:
1. deploy_vultr.sh API_BASE rewrite mismatch with current frontend source
2. No default TLS-enabled production path
3. Root-run backend service in deployment script
4. Unverified MediaPipe/OpenCV runtime compatibility in current slim Docker image
5. Persistence not explicitly provisioned for containerized deployment

## Hosting Option Comparison
### Vultr VPS
Pros:
- Full control over system libs needed by OpenCV/MediaPipe
- Easy static frontend + Nginx + FastAPI co-hosting
- Straightforward persistent storage with local disk
- Predictable uptime and behavior for portfolio demo

Cons:
- More ops responsibility (security patching, backups, TLS setup)
- Script needs fixes before safe use

### Render
Pros:
- Simple Docker deploy and managed runtime
- Good developer UX

Cons:
- Persistent disk and instance behavior must be carefully configured for SQLite
- Vision/native dependency behavior can be trickier than VPS
- Cold-start/plan constraints can affect demo reliability

### Railway
Pros:
- Fast setup and good DX
- Docker-friendly

Cons:
- Ephemeral filesystem patterns can conflict with SQLite persistence unless volume strategy is explicit
- Native dependency predictability varies by environment

### Fly.io
Pros:
- Strong Docker support
- Persistent volumes available
- Good for globally accessible demos

Cons:
- Operational complexity is higher than Render/Railway
- SQLite requires disciplined single-writer + volume placement

## Recommended Hosting Platform
Recommendation for this specific app: Vultr VPS

Reasoning:
- Best fit for OpenCV/MediaPipe native library control.
- Easiest way to co-host static frontend and FastAPI with Nginx.
- Works well with current SQLite architecture for single-instance portfolio demo.
- High reliability for live demo if TLS + service hardening are applied.

Second choice:
- Fly.io with a single instance and persistent volume, if you want platform-managed deploy flows and can accept added ops complexity.

## Deployment Requirements Checklist
Before deploying publicly:
- Fix deploy_vultr.sh API base rewrite behavior against current frontend source.
- Configure APP_ENV=production and strong JWT_SECRET_KEY.
- Configure CORS_ORIGINS to real frontend domain.
- Enable HTTPS and redirect HTTP to HTTPS.
- Run backend as non-root user.
- Validate MediaPipe/OpenCV on target host image.
- Ensure persistent storage and backup for communication_bridge.db.

## Production Deployment Plan
Phase 1: Pre-deploy hardening
- Finalize .env production values.
- Prepare TLS/domain.
- Validate Nginx to backend proxy and frontend static routing.
- Verify frontend API base points to deployed /api path.

Phase 2: Deploy
- Deploy single backend instance.
- Serve frontend via Nginx.
- Confirm DB file persistence path and permissions.

Phase 3: Smoke and feature verification
- Health endpoint response.
- Auth signup/login cycle.
- Session creation and message flow.
- Gesture endpoints with sample payloads.
- LLM path with valid GEMINI_API_KEY.

Phase 4: Stability pass
- Restart services and confirm data survives.
- Check logs and error rates.
- Verify browser webcam/microphone workflows over HTTPS.

## Post-Deployment Testing Checklist
- GET / returns healthy status.
- /auth/signup and /auth/login function correctly.
- Authenticated endpoints reject missing/invalid tokens.
- CORS allows only approved origin(s).
- Static frontend loads and calls API successfully.
- /vision/process-frame works with a sample frame payload.
- /vision/interpret-gesture returns contextual response.
- SQLite data persists across service restart.
- Nginx access/error logs show no critical misroutes.
- TLS certificate is valid and HTTP redirects to HTTPS.

## Rollback Plan
If deployment fails:
1. Keep previous working release artifact/config snapshot.
2. Repoint Nginx to previous backend service build/path.
3. Restart Nginx and backend service.
4. Restore last known-good SQLite backup if schema/data corruption occurred.
5. Re-run smoke checks on root, auth, and simulate/vision endpoints.
6. Keep incident notes and patch forward in a controlled redeploy.

## Final Decision
READY AFTER FIXES

Rationale:
- The repository has a viable architecture for a live portfolio demo.
- Current deployment assets are close but still have concrete safety and functionality blockers that should be addressed before public launch.
